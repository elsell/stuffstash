# Conversation Workflows and Evaluation

## Domain and ownership

Conversation workflows belong to the agent/model bounded context. A tenant owns each workflow, its immutable revisions, reusable evaluation cases and evaluation runs. Production chooses the active workflow revision for the tenant; each conversation snapshots that revision. Changes to a draft never modify a running conversation. The application validates provider profile ownership and capabilities before saving or activating a revision.

## Workflow definition

A workflow definition contains a display name, optional conversation model profile, general instructions, and model-call, tool-call, processing-time and follow-up limits. The model chooses tools, resolves ambiguity and authors its response through the conversation port described in [Model-led voice loop](model-led-voice-loop.spec.md). Transcription and speech continue to use the tenant's configured capability profiles. Domain services retain ownership of authorization, validation, approval, execution and audit.

Model/tool/time budgets apply independently to each user turn; follow-up limits apply to the session. Bounds are positive and no greater than environment-backed operator limits. Blank names, oversized or malformed text and profile references, and unsupported capabilities are rejected. Definitions are immutable snapshots. New writes reject retired stage, retrieval, response and attempt fields. Provider incompatibility fails preparation without changing the selected provider.

Historical persisted definitions convert at the persistence adapter as specified in the model-led loop migration contract. Retain the chosen model and useful general guidance, disclose conversion on the revision, and discard obsolete stage rules. Conversion preserves identity and attribution and does not revive a legacy executor or validate old evaluation evidence.

## Revision and activation

Workflow identity and revision identity are distinct. Saving creates a new numbered revision, with author and injected-clock timestamps, using optimistic concurrency. Activation checks ownership, compatibility and that the candidate has a completed passing evaluation for the selected test suite and current provider configuration. The active pointer changes atomically with audit. A previous revision can be activated for rollback with the same authorization checks. Deleting or disabling a provider used by an active revision must surface a clear precondition or unavailable state, never silently switch models.

## Test cases and runs

Cases contain a title, text utterance or audio attachment, isolated inventory fixtures and outcome expectations. Expectations include result kind, referenced fixture assets, location/containment facts, proposed commands, clarification requirements and forbidden mutations. Avoid exact prose comparisons as the default judge. Include default examples for tagged baby clothes, existing-item moves, an explicitly additional item, ambiguous duplicates, speech failure and follow-up references.

Runs snapshot revision, provider configuration identity (never credentials), case versions and operator budgets. A leased background worker executes cases through the same conversation service, records bounded safe stage events, outcomes, call counts and timings, and honors cancellation between and during provider calls. Run states are queued, running, succeeded, failed, cancelled. Recovery after worker loss must not repeat real inventory mutations; evaluation uses fixture repositories and simulated command execution by default. The API exposes queued/running state without holding a request open.

### Durable run lifecycle

An evaluation run owns an immutable workflow revision, one to 100 distinct case revisions from its tenant, the current operator workflow limits and an author. Case order is fixed. The conversation model records one resolved profile ID and a 64-character lowercase SHA-256 configuration identity; an omitted default profile reference is resolved before queueing. Each run also pins the current runtime contract; historical runtime evidence cannot activate a revision. A configuration identity describes the effective non-secret provider configuration and credential version identity, never credential material. Execution rechecks configuration identity and authorization before dispatch; drift fails the run rather than switching providers or silently evaluating a new configuration. The first run coverage is explicitly text-only.

Run state starts queued with version one. Lease acquisition uses a new bounded opaque token, positive duration, and application-supplied clock time. Only queued runs or running runs with expired leases can be claimed. Each claim increments the attempt count and version; the caller supplies a bounded positive maximum claim count when queueing. Claim recovery preserves completed case results and resumes the first unfinished case. Expired owners cannot renew, record outcomes or terminate a run. A lease token alone does not replace repository compare-and-swap: all persistence transitions compare the stored version, and a reclaimed lease fences late writes from the previous worker. Worker loss may repeat an unfinished isolated model call; it cannot repeat approved inventory mutations because evaluations grant no approval.

Results arrive in case order and contain a validated structured observation, nonnegative elapsed duration and bounded model-call count. The domain computes the verdict from the pinned case; callers cannot supply a passing flag. Invalid observations are rejected, not treated as expected provider failures. Assertion failures remain visible while later cases run. The final case makes the run succeeded only if every verdict passed; otherwise it becomes failed. Terminal transitions clear the lease and record completion time. Authorized cancellation immediately fences queued/running work and becomes cancelled; repeated cancellation is idempotent. Worker infrastructure failures use a closed safe failure code set, not provider error text. An expired final attempt can be marked failed by recovery without accepting the expired worker's result. Every accepted state change increments the run version, uses nondecreasing supplied time and preserves defensive copies of mutable collections. Repository and worker implementations must prove CAS, cancellation, lease expiry and partial-progress recovery through their own boundary tests before release.

Tenant configure permission owns workflow/case/run mutation and trace access. Real inventory read evaluations require the selected inventory's view permission as well. Every mutation is audited; read audit follows existing lifecycle contracts. Trace records redact credentials, provider transport payloads and inaccessible data. Operator configuration controls retention and maximum concurrent runs. Evaluation instructions cannot grant tools or disable policy.

## REST and web surfaces

Evaluation case REST operations use `/tenants/{tenantId}/conversation-evaluation-cases`: POST creates revision one, GET lists current case heads, GET `/{caseId}` retrieves the current revision, GET `/{caseId}/revisions/{revisionId}` retrieves an immutable revision, and POST `/{caseId}/revisions` appends with a required positive `expectedRevision`. Creation/appends return 201, scoped misses 404 and stale appends 409. Every operation requires tenant configure permission, including reads of fixture data; inventory ownership or view permission is insufficient. Authentication/authorization precede case lookups and ID allocation. Bodies use separate camelCase DTOs with full fixture/expectation fields, including exact proposal details. Invalid definitions return standard validation errors and cannot persist a head or revision.

Lists use the server's pagination defaults with a ceiling of 100, tenant/collection-bound opaque cursors, and accurate `hasMore`/`nextCursor` metadata. A full maximum-size page uses one bounded existence probe rather than exceeding the repository limit. Reads emit `conversation_evaluation_case.viewed` and lists emit `conversation_evaluation_case.listed`; audit metadata contains case/revision identity or returned count, never utterances, fixture text or provider credentials. Read audit failure prevents a successful response. Revision creation retains the existing atomic repository/audit contract. Creation emits a domain-oriented observer event through the injected observer port.

Tenant-scoped collections: conversation workflows, workflow revisions, evaluation cases and evaluation runs. Explicit activation and cancellation operations are audited application commands. List/read/create/update requests use consistent envelopes, generated contracts and cursor conventions; revision updates reject stale expected versions.

The web workspace offers a default workflow summary, draft editor with one model, guidance and processing limits, test-case editor with fixture assets/tags/containment, run progress, side-by-side revision comparison and activation/rollback. Surface provider compatibility, estimated limits and actual usage without showing secrets. Runtime behavior is previewed through real test execution rather than a separate mock UI. Use existing SvelteKit, TanStack ownership and frontend ports/adapters.

## Evidence gates

The first isolated executor supports text cases. A project-owned execution port receives an immutable case/revision snapshot, current operator limits, the authorized principal and already-resolved provider bindings. Its adapter creates fresh in-memory tenant/inventory storage per execution, seeds fixtures through asset/tag application commands, and invokes the production realtime conversation service. A read-only workflow repository presents the candidate revision as selected within that isolated runtime without activating it in production. No live inventory repository or approval capability is supplied to the executor. The worker application must authorize tenant configuration before resolving providers or invoking this internal port.

Text cases use an explicit transcript bridge and discarded speech output; they make no recognition or synthesis calls and report text-only coverage. They are not audio-quality evidence. Actual model invocations through the selected profile are counted, including failures, and duration uses the injected clock. Completed response artifacts and stored unapproved commands are projected through the shared evaluator. A provider-stage failure may be an observed failure with a safe code, while fixture setup, configuration, cancellation and invalid observation errors cannot pass an expected-failure case. Every run verifies that its seeded assets, assigned tags and current checkout records remain unchanged after execution. Cancellation propagates through the same provider context; no approval is sent. A run must receive a completed response or an unapproved proposal, rather than infer success merely from a nil service error.

Domain validation and immutability tests precede implementation. Persistence/migration, application command/query, adversarial REST, worker cancellation/recovery, web adapter/UI and shared executor tests follow their responsibilities. Live ADC-backed cases exercise real audio, schema requests and speech alongside controlled fixture data. Run the same cases against a compatible local model where available; unavailable credentials/models are reported as verification limits rather than passed support. Release and device gates remain defined in voice-conversation-quality.spec.md.

## Persistence contract

Store workflow identity separately from revision snapshots. Every lookup requires tenant ID; revision lookups additionally require workflow and revision IDs. Workflow IDs and revision IDs are nonempty bounded opaque identifiers using ASCII letters, digits, underscore or hyphen. Author references preserve the established principal format: Unicode letters/digits, period, underscore or hyphen. Tenant references preserve the established tenant identity contract and are required to be nonblank; workflow identifier syntax does not redefine tenant IDs. A revision has a positive sequence number, immutable validated definition, author and nonzero creation timestamp supplied by the injected application clock. Rehydration must validate definitions against the recorded revision limits rather than reinterpret old revisions using changed defaults; activation separately checks current operator limits.

Appending a revision compares the expected latest sequence and atomically stores the revision, updates the workflow head and records audit. Concurrent saves must produce one winner and a conflict, never overwrite immutable history. Activating compares expected active revision and atomically updates the active pointer with audit. An active revision must belong to the same tenant and workflow. Persistence adapters must implement these operations transactionally, with production PostgreSQL migrations and SQLite parity tests. No direct application SQL is permitted.

Workflow revision appends emit `conversation_workflow.revision_created`; activation/rollback emit `conversation_workflow.activated`. Both actions are valid persisted audit actions. Safe metadata includes workflow/revision identity and sequence, not prompt bodies or credentials. Transactional repository commands reject audit records whose tenant differs from the workflow tenant. A missing workflow/revision is a normal scoped read miss; stale writes return a conflict sentinel that application adapters map consistently.

Migration rollback removes workflow tables but retains the expanded audit-action allowance, preserving historical audit records. It must not delete audit history to downgrade the schema.

Saving a draft validates its explicit provider reference for tenant ownership and language-inference capability. Empty references retain the tenant-default selection intent; the current default need not be configured to save a draft. Activation and execution must resolve defaults and require usable compatible profiles. Draft saving is authorized before ID generation, provider lookup or repository mutation. Returned revisions contain no credentials. A stale expected sequence maps to the standard application conflict error.

## Draft REST boundary

`POST /tenants/{tenantId}/conversation-workflows` creates the first immutable draft revision. `POST /tenants/{tenantId}/conversation-workflows/{workflowId}/revisions` appends a revision using a required positive `expectedRevision`. Both return 201 with a revision envelope containing workflow/revision identity, sequence, author, timestamp and the normalized definition. They require an authenticated principal with tenant configure permission; tenant membership or inventory ownership alone is insufficient. Missing workflows return 404, stale expected revisions return 409, and incompatible or inaccessible provider references return validation errors without disclosing provider details. Draft creation does not activate a workflow. Definition fields use camelCase transport names and remain separate from domain types.

## Operator workflow limits

Runtime configuration captures operator limits at startup. `STUFF_STASH_WORKFLOW_MAX_TOOL_CALLS`, `STUFF_STASH_WORKFLOW_MAX_MODEL_CALLS`, `STUFF_STASH_WORKFLOW_MAX_ELAPSED_SECONDS`, `STUFF_STASH_WORKFLOW_MAX_FOLLOW_UP_TURNS`, `STUFF_STASH_WORKFLOW_MAX_NAME_RUNES`, and `STUFF_STASH_WORKFLOW_MAX_INSTRUCTION_RUNES` default respectively to 12, 12, 60, 8, 100 and 4000. Unset or blank current settings use defaults. Nonblank values must be positive integers; invalid values prevent startup with a named safe error. Retired evidence-round and step-attempt environment keys are rejected with migration instructions. Configuration is captured once, and programmatic zero-value configuration uses the same defaults. Saved workflows specify budgets within these ceilings.

The in-memory runtime adapter must preserve the same scoped immutable revisions, compare-and-swap conflicts and atomic audit semantics as persistent adapters. Concurrent appends permit exactly one winner for an expected sequence. Duplicate audit identities and invalid cross-tenant audit records must fail before changing any workflow state.

## Fixture case definitions

Saved evaluation cases have tenant-scoped case identities and immutable revision identities, a positive sequence, author and injected-clock creation time. Case/revision IDs and author references use the same identifier grammar as workflow revisions. Saving atomically compares the expected latest sequence, appends the validated case definition, updates the case head and writes `conversation_evaluation_case.revision_created` audit. Concurrent or stale saves conflict; audit failure leaves both revision and head unchanged. Case heads retain the current title and revision identity for bounded list queries. Reads require tenant ID, and revision reads additionally require case ID. Lists order by case ID and accept an exclusive case-ID cursor with a limit from 1 through 100. Immutable revisions preserve fixture definitions used by queued or historical runs even when the case is edited later. PostgreSQL migrations and the in-memory adapter must preserve the same scoping, conflict, snapshot and audit guarantees. Downgrade removes case tables without erasing historical audit entries.

A fixture case definition has a display title, one text utterance, at most 100 fixture assets, and structured expectations. This text definition is the first case input; audio case transport remains a separate required follow-on. Fixture asset identities are local opaque IDs (the workflow identifier grammar), never live inventory references. Each fixture has item/container/location kind, title, optional description, assigned tag display names and an optional parent fixture ID. IDs are unique; parents must exist; containment must be acyclic. Case titles are bounded to 160 runes, utterances to 4000 runes, descriptions to 2000 runes, and tags use the established 32-name/80-byte voice evidence bounds. Fixture asset titles and proposed creation titles must be valid UTF-8 and fit the production asset title limit of 160 bytes after trimming; accepting a larger Unicode title would save a case that production fixture setup or command execution cannot accept.

Expected outcomes are answer, clarification, proposal or failure. Expectations may require references to fixture assets and containment facts expressed as asset/ancestor pairs. Such references must resolve inside the fixture; expected containment must agree with its parent chain. Proposed operation expectations use existing inventory operation vocabulary. A proposal expectation requires at least one proposed operation; other outcome kinds cannot require a proposal. Forbidden operations cannot also be required. No expectation executes a mutation. Definitions own defensive copies of nested collections so queued case snapshots cannot change under a running evaluation.

Fixture containment paths are limited to 32 assets to remain executable within voice evidence bounds. Proposed and forbidden operation expectations use mutation operations only; duplicate expectation entries and contradictory requirements are rejected.

Fixture parents must be containers or locations, matching production containment. An item cannot be a parent, and evaluation setup must not silently convert its kind.

## Outcome evaluation

The application projects completed structured responses and persisted approval proposals into fixture observations. A completed structured response requires nonblank spoken and display content, including a safe-failure response; an empty response cannot pass an expected-failure case. Runtime asset IDs map through an explicit one-to-one fixture identity map; unknown IDs fail observation mapping. Retrieval alone is not an answer. References must come from the completed response's displayed asset artifacts. A direct containment assertion additionally requires displayed child and parent artifacts, with the child's application-grounded context matching that fixture parent's title. Fixture hierarchy alone cannot supply missing response evidence. Deeper containment is not inferred from an undisplayed ancestor.

Proposal projection consumes complete persisted command records, not user-facing command summaries (which omit target IDs and some arguments). Every semantic argument must be represented in the case assertion. Unknown command kinds, unknown arguments, malformed/non-string arguments, duplicate JSON keys, external fixture IDs and new-parent command references fail mapping. Create-location defaults and create-asset item defaults match production command semantics; checkout/return details are retained. Projection errors are invalid observations, never a successful expected provider failure. The projector owns a copy of the fixture identity map and validates it is a bijection over the complete fixture set.

The deterministic case evaluator compares application-observed outcomes, not model self-reports or exact prose. It checks outcome kind, required fixture references, required containment facts and required proposed mutation operations. Forbidden operations fail if proposed or executed. Any executed mutation fails the default fixture evaluation contract, which observes approval proposals without granting approval. Additional valid references are allowed unless separately prohibited by a future expectation. Unknown fixture references, invalid outcome kinds and malformed operations fail as invalid observations rather than counting as a passing expected failure. Results contain typed failure codes and safe fixture/operation identifiers; raw model text is not needed to judge these expectations.

Proposed mutation operation types form a closed expected set: every required type must occur and no unrequested type may be proposed. This prevents a requested move from passing alongside an unrequested archive. Exact proposal targets and arguments must additionally be checked by the evaluation runner's command assertions before this can serve as a complete action-quality gate.

## Exact proposal assertions

Proposal expectations use complete structured commands rather than operation names alone. Each command specifies mutation operation, existing target fixture ID where applicable, destination fixture ID where applicable, and new title/kind for creation. Existing targets and destinations must belong to the fixture; destinations must be containers or locations. Create commands use a new title/kind and cannot target an existing fixture ID. Non-create commands cannot carry creation fields; only create/move may carry a destination.

The judge compares the entire unordered collection, including command count. Wrong targets, wrong destinations, changed creation fields, extra commands and duplicate commands fail even when the operation type matches. Identical expected commands are rejected as an invalid case. Raw runtime IDs must be mapped to fixture IDs by the runner before judging. This replaces the preliminary operation-only proposal assertions; forbidden mutation rules remain operation-based.

Checkout and return assertions include the exact trimmed details text (at most the existing 500-rune voice detail bound). Other operations reject this field. The runner must fail observation mapping for semantic command arguments it cannot represent, including new-destination command references until graph assertions are implemented; it must never discard unsupported arguments and report an exact match. The current create compiler emits title/kind/parent only.

## Tenant workflow selection

A tenant has at most one selected workflow revision for production voice. Selection is an explicit tenant-scoped record containing workflow and revision identity; it is never inferred from draft update timestamps. Activation atomically compares the caller's expected tenant selection (both workflow and revision, or empty for none), updates that selection and the selected workflow's activation pointer, and writes audit. A stale activation conflicts even when switching between different workflows. Saving a draft cannot change selection. Sessions read and pin the selected immutable revision at start. An absent selection uses the documented default workflow. Selection must reference a revision belonging to that tenant and workflow.

## Model execution and session preparation

The shared production/evaluation conversation loop counts each model invocation and tool dispatch against the current user turn. There are no separate interpretation, assessment, response or semantic-repair executors. A stateless wrapper supplies pinned model guidance. Processing deadlines cover transcription, model/tool work and speech output after the submitted utterance; waiting for the next utterance consumes no processing allowance. Cancellation propagates, late model results are rejected, and terminal failure persistence uses bounded cleanup independent of an expired processing deadline.

After tenant and inventory access checks, session setup reads the selected revision through the workflow application service, which independently requires tenant view permission. No selection uses the default flow. A broken selection or out-of-limits revision fails closed. The selected revision and conversation provider remain pinned for the session.

Explicit profile resolution uses a tenant-scoped project-owned resolver. The exact profile must be enabled, configured, tested and language-capable. Unknown, foreign or unusable profiles fail without substitution. When a workflow selects an explicit model, no unused default language model is required or constructed. Speech recognition and synthesis retain their configured resolution. Profile guidance and general workflow instructions both reach the conversation provider.

Authorized fuzzy search, detail, vocabulary and other available reads are tools chosen by the model. No mandatory exact-search pass, evidence rounds or prescribed clarification response remains. The bounded context, tool contracts and observed-reference checks in the model-led loop specification govern evidence delivery without classifying requests or rewriting model prose.

The durable run domain caps claim attempts at ten; runtime configuration may select a lower positive value. Current runs pin exactly one conversation provider. Historical fingerprints remain readable data under their legacy runtime marker and cannot be executed or activated. A historical profile cannot claim inconsistent configuration identities within one run.

Persisted runs must be rehydrated through domain validation before worker or user-facing use. Rehydration validates the immutable input again, result ordering and pinned revision identities, recomputes verdicts from observations, checks nonnegative bounded metrics, and rejects impossible state/lease/timestamp combinations. Persisted passing flags are not trusted. It owns defensive copies just like newly queued runs. Queued state cannot carry results or a lease; running state needs a live-at-last-update lease and unfinished cases; terminal states clear leases and have a completion timestamp equal to their last update. Infrastructure failure codes apply only to incomplete suites. Storage adapters map infrastructure records to these domain values rather than bypassing validation.

A repository update must be an exact successor of the stored run, not merely a valid standalone snapshot with the next version. The domain validates successors by replaying the claimed transition from the previous aggregate and comparing the complete resulting snapshot. This preserves immutable inputs and completed result prefixes, fences terminal runs, and prevents combined or fabricated transitions from bypassing lease rules. Complete structural value comparison is intentional here: newly added snapshot fields must not silently escape successor validation. Persistence adapters enforce the expected version and this domain policy atomically with the audit record.

Successor comparison treats timestamps as instants, canonicalizing time zones and removing process-local monotonic metadata before complete structural comparison. A persisted/reloaded predecessor must accept the same valid successor as its in-memory equivalent. This normalization applies only to time representation; it cannot normalize away changed identities, instructions, results, metrics or policy.

## Durable run repository contract

The run repository exposes tenant-scoped single-run reads, bounded tenant head lists, atomic versioned saves with audit, and bounded operational discovery of runnable references. Tenant list/read methods never infer tenant identity from a run ID. Head lists order by run ID with an exclusive ID cursor and limit 1–100; heads contain status, version, workflow/revision identity, total/completed/passed cases and timestamps, without fixture or prompt bodies. Operational discovery is an explicit queue exception: it returns tenant/run references for queued or lease-expired running runs, ordered by creation time and then tenant/run IDs, at most 100. Discovery grants no lease; workers must claim through versioned domain transitions and atomic persistence.

Creation accepts only a validated queued version-one run with expected version zero. Updates require exactly the next version and `IsSuccessorOf` the stored aggregate. Load the predecessor and enforce the version predicate inside the same transaction as the update and audit insertion; a concurrent writer must produce a conflict. Missing updates, stale versions, overwritten identities or invalid successors cannot modify state. Duplicate audit records roll back the complete operation. Audits require matching tenant and run target and no inventory scope: `conversation_evaluation_run.created` for queueing, `conversation_evaluation_run.cancelled` for cancellation, and `conversation_evaluation_run.progressed` for other transitions. Safe metadata contains state and progress counts only.

Persist immutable input separately from mutable progress. Input includes full workflow and case definitions, their immutable identities, resolved non-secret provider configuration identities and operator limits. Saving progress must not rewrite the input payload. Infrastructure serialization uses explicit records to preserve private domain value objects; decoding reconstructs revisions and calls run rehydration. Queryable status/version/lease/head fields must agree with decoded progress. Store a tenant foreign key and an index supporting status/lease discovery. PostgreSQL migration and SQLite schema parity are required; downgrade must preserve historical audit allowances. The in-memory implementation must preserve the same conflict, atomic audit, immutable history and queue semantics. Tests must exercise timestamp round trips, rich definitions, tenant isolation, concurrent claims, cancellation versus stale completion, failed audit rollback and bounded discovery before worker wiring.

Run JSON snapshots preserve exact domain instants. Indexed SQL timestamp columns use UTC microsecond precision to match PostgreSQL storage; column-to-payload validation compares that canonical representation. Discovery may return a run within one microsecond of lease expiry, but the domain's exact lease check still governs claiming. Round-trip tests must include non-microsecond timestamps so production reads cannot fail only because SQL normalizes precision.

Memory head timestamps and runnable ordering use the same UTC microsecond representation as SQL; exact input timestamps remain available on the run snapshot. Sub-microsecond creation differences therefore tie consistently and use tenant/run identity ordering in every adapter.

Conversation audit targets are typed domain values: `conversation_workflow`, `conversation_evaluation_case`, and `conversation_evaluation_run`. PostgreSQL constraints and audit rehydration must accept all three while retaining existing targets. Migration tests must use the actual conversation targets, and repository conformance must read back persisted audit records; an unrelated asset target cannot stand in for these operations. Downgrade preserves historical target allowances.

## Authorized run commands

Queueing requires tenant configure permission before any revision lookup, provider access or ID allocation. The caller supplies one explicit workflow/revision pair and 1–100 explicit case/revision pairs; latest-revision substitution is forbidden, and duplicate case IDs are rejected. Application code loads each revision through its tenant-scoped repository, resolves non-secret provider configuration snapshots through a project-owned port using that workflow, and constructs the run with injected time, IDs and operator limits. Missing revisions return not found; unavailable provider configuration fails without creating a run. Provider snapshots must identify the exact effective configuration and credential version; no credentials or provider objects are persisted. Production wiring of the resolver must precede exposing queue commands.

Creation persists queued version one and its audit atomically. Cancellation requires the same permission and an explicit expected run version, including for an already cancelled run. A matching already-cancelled request is idempotent and emits no second mutation audit; other terminal states or stale versions conflict. Cancellation reads within the tenant and uses the domain transition plus repository CAS so concurrent worker completion cannot be overwritten. Safe command audit metadata contains only state and progress counts. These commands do not invoke a model or grant approval to inventory changes. Application tests cover denied and unauthenticated requests, missing/cross-tenant revisions, provider failure, duplicate cases, immutable pinning, stale cancellation and audit atomicity; HTTP boundary tests are required when those commands are exposed.

Provider snapshot resolution uses production voice's ready-profile selection policy. It resolves the tenant default only when the workflow omits an explicit conversation profile. The selected profile must belong to the tenant, be enabled, tested and language-capable. A versioned vault and factory identity implementation are required. Snapshotting makes no model or speech calls and cannot substitute another provider. The result contains one profile ID and effective configuration identity, with no stage name. Invalid tenant scope, profile readiness, credentials or identity support fails the snapshot.

Worker provider resolution accepts the validated run and explicit tenant scope, reloads only its pinned profile IDs, and verifies every effective fingerprint before constructing any provider. It must not reselect a new default. The pinned profile is loaded and constructed once. A changed/missing/unusable profile or fingerprint yields a typed configuration-changed error; infrastructure read failures remain errors. The returned execution-only bundle supplies the pinned default language provider where needed and a tenant-scoped immutable resolver for the explicit model. That resolver admits only profiles from this run. No returned provider bundle is persisted. Changing the tenant default after queueing cannot redirect a run.

## Evaluation worker processing

The application worker loads an operational tenant/run reference and atomically claims a queued or expired run with a fresh lease token. A live lease or terminal run is skipped. An expired run that has exhausted attempts is atomically failed as worker-lost. Claims, renewals, results and failures each persist one domain transition with a system audit. Resume starts after the persisted completed-case prefix.

Before resolving providers and before each case, check the original author's current tenant configure permission. Denial terminates the run as access-revoked; authorization infrastructure failure does not masquerade as denial. Resolve the pinned execution bundle once per claim; configuration drift terminates as configuration-changed. Each case uses the existing isolated executor with the pinned workflow/case, limits and author principal. Text-only results retain their coverage limitation. Enforce the workflow elapsed budget through a case context deadline; the lease includes configurable positive grace for persistence and is renewed between cases. Successful results are recorded through the domain verdict evaluator. Invalid execution results or executor failure terminate as execution-failed, rather than passing an expected model-failure case.

Reload the run before each case and before recording an outcome. Cancellation or another version/lease owner stops processing and suppresses late results; CAS remains authoritative against races after reload. Parent shutdown leaves the current lease recoverable. Queue draining, active cancellation polling during model calls, operator configuration and bootstrap wiring remain required before deployment; this processing service alone must not be exposed as the finished worker.

Worker configuration validates elapsed seconds against the duration representation before multiplication and grace against the remaining range before addition. Overflow, including positive wraparound, is a precondition failure before claiming a run or accessing providers.

During each executor call, the worker supervises its lease/version and the author's current configure permission at an injected positive polling interval. Waiting is behind a context-aware delay port, separate from the injected domain clock. Lost lease, cancellation or revoked access cancels the executor context promptly; no late observation is persisted. A supervision infrastructure error cancels execution and leaves the lease recoverable rather than claiming access was revoked. Stop and join supervision when the executor returns so no goroutine outlives its case. Recheck access after execution before committing results. Production executor/provider adapters must honor context cancellation. The timer adapter uses cancellable standard timers; tests use controlled pulses rather than wall-clock sleeps.

Queue draining discovers at most the caller's bounded 1–100 runnable references and processes them with an operator-selected concurrency of 1–8 per API process. Each run still acquires its own repository CAS lease; discovery grants no ownership. A failed run must not prevent other discovered runs from being processed. Return combined errors only after in-flight processing stops, and propagate shutdown cancellation. Queue draining is serialized by the bootstrap scheduler within a process so periodic ticks do not multiply concurrency. Defaults must favor small local providers: one concurrent run. Runtime scheduling/configuration remain a separate integration step.

Runtime evaluation settings are captured from the environment before application construction and reject malformed/out-of-range values at startup. Worker defaults are enabled, drain limit 10, concurrency 1, drain interval 5s, active poll interval 2s, lease grace 30s, and maximum claim attempts 2. Environment keys use the `STUFF_STASH_EVALUATION_` prefix with `WORKER_ENABLED`, `DRAIN_LIMIT`, `CONCURRENCY`, `INTERVAL`, `POLL_INTERVAL`, `LEASE_GRACE`, and `MAX_ATTEMPTS` suffixes. Limits are 1–100 runs, 1–8 concurrent runs, 100ms–1h drain interval, 100ms–30s polling, 1s–5m grace, and 1–10 attempts. Disabling this process's worker leaves persisted work available to another worker process. Serial periodic draining prevents overlapping batches in one process.

Bootstrap assembles command and worker application services from the configured repositories, current authorizer, provider vault, configured profile resolver, isolated executor, clock, ID generator and observer. The compatibility application facade only delegates. The worker must not receive production inventory repositories through its executor. Scheduler failure telemetry uses a fixed safe event/category, never raw provider errors or test content.

Tenant evaluation-run reads require configure permission before repository access. Single-run reads return the validated run; bounded head lists use tenant/collection-scoped opaque cursors and preserve the existing 1–100 page contract, including a probe for exactly full pages. Successful reads append `conversation_evaluation_run.viewed` or `conversation_evaluation_run.listed` audit records with the run target type. Audit failure suppresses the read response. Metadata contains only returned counts or run identity, never fixture content, prompts, observations or lease tokens. REST mapping must use explicit response fields and never serialize the persistence snapshot directly.

## Evaluation run HTTP contract

Expose tenant configure-authorized `POST` and `GET /tenants/{tenantId}/conversation-evaluation-runs`, `GET /tenants/{tenantId}/conversation-evaluation-runs/{runId}`, and `POST /tenants/{tenantId}/conversation-evaluation-runs/{runId}/cancellation`. Queue returns 201 with the newly persisted queued resource, not a completed evaluation. The queue body contains `workflowId`, `revisionId`, and 1–100 `cases` containing `caseId` and `revisionId`. Provider identities, author, limits and leases are server-owned. Cancellation accepts positive `expectedVersion`, returns the resulting resource with 200, and reports stale versions as 409. Missing or foreign references are 404 after authorization; callers without tenant configure permission receive 403 before resource discovery. Anonymous and malformed authentication receive 401.

Lists use standard envelopes and opaque cursor pagination, returning explicit head fields. Detail responses expose run identity, state/version, pinned workflow/revision, author, timestamps, counts, pinned case identity/title and non-secret provider configuration identities. Completed results include observations, verdict failures, model-call counts and duration in milliseconds. Coverage is explicitly `text_only`; these runs cannot claim microphone, transcription, synthesis or device verification. Responses must never serialize raw persistence snapshots, input/progress JSON, lease tokens, credentials or operator configuration. Security tests exercise all four routes, authorized operation, tenant isolation, version conflicts, pagination and explicit field projection before implementation.

## Activation evidence validation

Activation selects an explicit candidate workflow revision, a completed successful run, and the exact set of case/revision pins chosen as the suite. The domain rejects pending, cancelled or failed runs; another tenant or workflow revision; missing, extra or duplicate suite pins; and any changed provider profile/configuration binding. Suite and provider ordering do not affect equality. Revalidate the candidate definition against current operator limits. A successful text run authorizes workflow selection only; it never upgrades its recorded coverage to audio or device evidence. Rollback uses the same gate against the earlier immutable revision and current provider configuration.

The application authorizes tenant configure before loading the candidate/run or resolving provider fingerprints. It reloads current fingerprints through the snapshot port without making inference calls, validates evidence, and atomically changes selection with its audit using the caller's expected previous workflow/revision pair. Empty previous pairs mean no selected workflow; partial pairs are invalid. Stale selection is a conflict, missing scoped resources are not found, and failed evidence/compatibility is a precondition. Audit metadata records candidate revision and evidence run identity, never prompts, fixtures or provider credentials. In-flight sessions retain their already pinned revision.

Expose activation as `POST /tenants/{tenantId}/conversation-workflows/{workflowId}/activation`, returning the activated immutable revision in the standard envelope with 200. The uniquely named body contains `revisionId`, `runId`, exact `cases` pins and an optional `expected` previous workflow/revision pair; omitted previous selection means none. Configure permission is mandatory. Test anonymous/malformed tokens, nonmembers, viewers, inventory owners and another tenant's owner, plus legitimate activation, queued evidence rejection, foreign evidence rejection and stale selection conflicts at HTTP. Bootstrap injects the same configured snapshot resolver and repositories used for evaluation, so HTTP activation cannot bypass the real provider fingerprint gate.

## Workflow discovery persistence

The workspace discovers workflows through tenant-scoped, bounded head pages ordered by workflow ID with an exclusive cursor. Each head includes the latest name and revision identity, latest sequence, active revision identity and timestamps. Persist the latest name and revision ID with the head and update them atomically on append, so listing does not fetch every revision or issue one query per row. Migration 45 backfills existing heads from their exact latest immutable revision. Immutable revision history is separately paginated in ascending sequence, scoped by both tenant and workflow. Both repository page limits are 1–100; invalid limits fail, empty pages are valid and cancelled reads stop. Memory and GORM adapters must agree on ordering, scope, latest metadata and revision history. Read authorization and audits remain application responsibilities.

Workflow discovery application queries require tenant configure permission before storage access and safe read audit before returning data. Support latest or explicit immutable revision reads, head pages, revision-history pages and the current tenant selection (nil means the default workflow). History cursors bind both tenant and workflow; head cursors bind tenant and collection. Current page limits remain 1–100, including accurate next-page detection at 100. Missing workflows/revisions return not found; invalid cursors return validation errors. Read audit actions are `conversation_workflow.viewed` and `conversation_workflow.listed`, with revision IDs or returned counts only. Audit failure suppresses the response. PostgreSQL migration 46 preserves all existing actions and adds these read actions.

Workflow read HTTP operations are `GET /tenants/{tenantId}/conversation-workflows`, `GET /tenants/{tenantId}/conversation-workflows/{workflowId}`, `GET /tenants/{tenantId}/conversation-workflows/{workflowId}/revisions`, `GET /tenants/{tenantId}/conversation-workflows/{workflowId}/revisions/{revisionId}`, and `GET /tenants/{tenantId}/conversation-workflow-selection`. Lists return standard paginated arrays; revision reads return the existing immutable revision DTO. Selection returns a nullable workflow/revision pair. Every operation requires configure authorization, uses scoped query services and safe read audit, and has adversarial endpoint coverage. Head DTOs expose names and latest/active revision identities without prompt bodies. Wire contracts remain generated from CI.
