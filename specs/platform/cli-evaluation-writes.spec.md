# Evaluation authoring and queueing through the CLI

`evaluation cases create --input FILE|-`, `evaluation revisions create CASE_ID --input FILE|-`, and `evaluation runs create --input FILE|-` expose the three evaluation write operations. They use household-only saved context and picker behavior and existing administrator authorization. No inventory selection is required.

All three require structured JSON via the existing bounded input port; no editor or scalar defaults are introduced. Case creation requires definition; revision creation additionally requires a positive int64 expectedRevision. Definitions contain title, utterance, optional assets, and expectations, with every declared fixture/expectation/proposal field accepted. Run creation requires workflowId, revisionId and 1–100 caseId/revisionId pairs. Optional schema, nulls and supplied integer values are forwarded unchanged as original bytes through generated SDK WithBody methods behind the evaluation port. Local validation rejects unknown fields, incorrect types, missing required structure and malformed revisions before authentication. The server retains domain-semantic validation.

Show the server, household, target and operation effect before confirmation. Revision confirmation includes supplied expectedRevision; queue confirmation includes the workflow revision and case count and explains that a background text-only evaluation may call configured model providers. Case writes do not activate a workflow. Scripts/JSON/no-input require --yes; interactive confirmation defaults to cancel. Never replace supplied versions with a lookup, retry writes, or activate a workflow as part of creation. Conflicts and uncertain results direct the user to inspect current case/run state before retrying; these operations have no idempotency-key contract.

Complete returned case-revision and run envelopes reuse the typed evaluation decoder and safe human/JSON presentation, including schema, metadata, nested values, nulls and numeric precision. Command help documents request fields and runnable examples. No dependencies, chat execution or raw generic request command are added.

Critical tests cover exact complete payloads and full responses, authentication/wrong-household denials, explicit CAS without a lookup, missing/declined confirmation without mutation, provider-work warning, invalid input before credentials, and conflict/uncertain failure without retry. Full CLI tests, relevant hooks and code critic are required before commit.
